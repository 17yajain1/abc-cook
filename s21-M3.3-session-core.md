## CP2 (`engine.ts`, `store.ts`, `useSession.ts`)

**`engine.ts`** — every action in the plan's §E table as `(session, model, now) -> session |
Rejected`: `start`, `open` (read-only, reports `SessionLifecycle`), `startNode`, `markDone`,
`acknowledge` (multi-entry, per the plan's §L1 refinement over the original single-entry
`Transition`), `skip`, `extend`, `undo`, `leave`, `resume`, `touch`, `end`. Never throws.

Two scoped decisions beyond the plan's literal preconditions, both documented in the file — and
both independently audited on 2026-09-22, one revised as a result (see below):

1. **Lifecycle gating is scoped to exactly `open`/`leave`/`resume`**, per the CP2 brief's own
   "IMPORTANT lifecycle boundary" note — not applied broadly to every mutator. Broadly gating
   `markDone`/`startNode`/etc. on `lifecycle() === 'active'` was considered and rejected: it would
   also block `undo` from reversing the very `markDone` that just set `finishedAt` (lifecycle flips
   to `finished` in the same instant undo needs to act), defeating undo's stated purpose. The
   2026-09-22 audit re-confirmed this scoping and found no other mutator needs it.
2. **`resume`'s only precondition is `leftAt != null`** — exactly §E's literal text, nothing more.
   The first CP2 pass additionally rejected `resume` when `lifecycle() === 'finished'`; the
   2026-09-22 audit found that rejection was not authorized by any line of §E/§K5/§L/§M and it was
   removed (plan § *N. Audit clarifications, 2026-09-22*, §N1). `resume` still succeeds from a
   `stale` reading unchanged — it is the engine action behind the plan's own "Continue" recovery
   path off a stale reopen (§C6: "a stale session is never resumed silently... offers Continue /
   Start again" — the operative word is *silently*). It also now succeeds from `finished`, which is
   safe rather than a hole: `lifecycle()` checks `finishedAt` first, unconditionally, so clearing
   `leftAt` cannot resurrect a finished session. `leave`'s gate is unchanged and is now an explicit
   plan definition, not an inference: §N2 resolves §E's undefined "session live" precondition as
   `lifecycle(model, session, now) === 'active'` — rejecting both `finished` (nothing to leave) and
   `stale` (the stale screen is the only thing shown until Continue/Start again).

**`store.ts`** — `createSessionStore(storage, now)`, the same injectable-storage/tolerant-read/
salvage pattern as `library/store.ts`. One session under `abc-cook:session:v1`. `dispatch(action)`
for every mutating action (each action carries the `CookingModel` it applies to — the store itself
is model-agnostic); `open(model, planKey, now)` is a separate, non-mutating read. No default clock
(`createLibrary`'s `now: () => Date = () => new Date()` pattern was *not* mirrored here) — a
default would put a literal `Date.now` reference in this file, and the plan's exit criterion 3 is
repo-wide (`grep -n "Date.now" apps/web/src/cooking` returns only `useSession.ts`), not just
engine/model/select.

**`useSession.ts`** — the `useSyncExternalStore` binding, and the only place `Date.now()` is
called. No dedicated test file: the plan's own CP1+CP2 file list (§G) names `model`/`engine`/
`select`/`store`/`constants` tests only, and hook rendering needs `jsdom`/`@testing-library/react`,
neither of which this project has (`vitest.config`'s `test.environment` is `'node'`) — adding one
would violate the CP2 brief's "no new dependency." Its logic is thin glue over `store.ts`, already
exercised by `store.test.ts`'s `dispatch`/`getState`/`subscribe` coverage.

## Test coverage added (CP2)

`engine.test.ts` (rows 3–6, 14, 16–28, 34, 36–37) and `store.test.ts` (rows 15, 34, 35, plus
dispatch/subscribe wiring) — 65 new cases, all driving the reducer through real `engine.*`/
`store.dispatch` calls rather than hand-constructed state (CP1's style, appropriate there since
CP1 has no reducer yet; CP2's whole point is the reducer, so its tests exercise it directly).

**Row 24 adapted, not reproduced literally.** The plan's original §H text ("skip
`make_kadai_masala`; do `cube_paneer`; base expires -> quiet") predates the §K3/§B5 must-attend
resolution CP1 already implements and tests (rows 9–10: a periodic host is required the instant it
expires, regardless of whether its consumer is blocked — never "quiet"). It is also unreachable by
real sequential actions on the kadai fixture: `cube_paneer` (execution order position 6) precedes
`make_kadai_masala` (position 7), so `make_kadai_masala` cannot be `current` — and therefore cannot
be `skip`ped — while `cube_paneer` is still pending. `engine.test.ts`'s row-24 test keeps the row's
actual point (a deferred node returns as `current` once nothing else is pending-executable, and
later completing it unblocks its consumer) using `chop_capsicum` instead, and asserts the handover
reason the K3 rule actually produces.

**Full-run determinism/invariants (rows 36–37).** A generic driver (`runToCompletion`) walks every
one of the eight fixtures to completion with one fixed strategy — acknowledge any pending handover,
otherwise act on `current` immediately, otherwise jump `now` to `nextRequiredAt` — and asserts
byte-identical JSON across two independent runs, every node ending `done`, `finishedAt` set exactly
once on the sink, and no hands-on node ever carrying a timer. It also throws a named error (rather
than looping) if it would ever hit the plan's §M3 reachability finding (something running while
`current` is null and `nextRequiredAt` is null) — none of the eight fixtures hit it, consistent with
§M3's own note that this state could not be constructed from any of them.
