## 1. Real visual evidence, not just timing numbers

The owner rejected `s12`'s `getAnimations()`-only verification: *"I need to actually
see the sweep, not just trust the timing data."* Fix: pause each animation
(`getAnimations()[0].pause()`) and scrub `currentTime` to a fixed value before
screenshotting — this freezes the frame deterministically, sidestepping the CDP
screenshot round-trip being too slow/flaky to land inside a ~650ms window at normal
speed. Captured Kadai Paneer and Chicken Biryani at multiple points through the sweep,
top and bottom of each map (`docs/design/renders/m275-anim-v2-*.jpg`).

**A wrong assumption this caught:** `s12` characterized Kadai Paneer as short ("cards
complete ~260ms") from a viewport that was never scrolled past "Make kadai masala."
Kadai actually has 10 tasks — `Add veggies`/`Add paneer`/`Finish` continue below the
fold — with a real max card delay of 316ms, nearly as tall a sweep as Biryani's 325ms.
Caught by reading the SVG's own `<desc>` and the full card list during this session's
verification, not assumed from an old partial screenshot.

## 2. Connector timing — derived per map, not a fixed 500ms

Owner's instruction: remove the fixed 500ms dead hold, but don't replace it with a
different fixed value either, since no single constant is both tight for a short
recipe and safe for a tall one. Fix, explained to the owner before implementing (per
instruction): `motion.ts` lost `CONNECTOR_DELAY_MS`; gained
`connectorDelayMs(cards, mapHeight) = max(entryDelayMs(card) for card in cards) +
FADE_MS` — exactly the last card's landing time, so the "no connector before its
endpoints exist" invariant holds by construction. `layout.ts` untouched, as instructed.

Measured, all satisfying the exact-match invariant: Maggi (short, serial) 411ms — the
real dead-hold win, down from 500ms; Kadai Paneer 466ms; Chicken Biryani 475ms.

## 3. Once per recipe

Verified the lifecycle claim before touching `PlanScreen.tsx`: `App.tsx` never
transitions directly between two `{kind:'plan'}` views — every recipe change passes
through `{kind:'loading'}` first (a different component at the same JSX slot), which
unmounts `PlanScreen`. Toggling `Plan ↔ Map` only flips local state in the same
instance. So a value living in `PlanScreen`, untouched by the toggle, is exactly
"once per recipe."

**Tried `useState` first — it's actively wrong, not just non-idiomatic.** Flipping
state in a `useEffect` right after the animated mount commits re-renders the same,
still-mounted `MapView` with `skipEntryAnimation=true` almost immediately, stripping
the animation classes mid-flight and snapping every card to full opacity — defeating
the animation on the one mount it's supposed to play on. Switched to `useRef`, whose
mutation triggers no re-render — a deliberate, documented exception to oxlint's
`react(refs)` rule (suppressed with an inline comment explaining why, not silently).
