# M2.9 — YouTube Import: Design Document

**Status:** Design, revision 3 — architecture approved by the owner (revision 2), and
Verification B (§10.C) has now actually been run against a real provider, producing one
binding new rule (§10.C) that revision 2 did not yet state explicitly. Implementation
begins on `feature/M2.9-youtube-import`, carrying this doc forward.

**Session date:** 2026-09-13 (design) + 2026-09-13 (Verification B, same calendar day,
next session)
**Branch:** `feature/M2.9-youtube-import` (design authored on
`feature/M2.9-youtube-import-design`)

**Thesis being tested:** not "we can import recipes" (ReciMe already proves that's
possible) but "a real recipe from a messy real-world source can become a `CookingGraph`
good enough that the existing scheduler produces a plan a cook would actually trust at
the stove." Import is the front door; the graph and scheduler are the moat.

**The principle this document is built around, stated once and referenced throughout:**

> **Optimize what we understand; do not hallucinate what we don't.**

Its corollary for every scheduling-relevant field: **uncertainty must cost parallelism,
never safety.** Prefer a missed optimization over an unsupported one.

## 0. Step 0 — what 15 real YouTube recipe videos actually contain

Before any design: a throwaway script (outside the repo, `yt-dlp --dump-json` against
15 owner-supplied URLs — Hindi, Gujarati, Bengali and English cooking channels) pulled
title + description verbatim, no parsing, no LLM. Read by hand.

| Bucket | Count | Videos |
|---|--:|---|
| **A. Full recipe** — ingredients + ordered steps + explicit durations | 2/15 | Pakoda Kadhi, Donuts |
| **B. Rich recipe** — ingredients + ordered steps + partial timing (incl. chapter markers) | 2/15 | Paneer Tikka Sandwich, Paneer Toast Sandwich |
| **C. Ingredients only** — no method text, no blog link | 6/15 | Gulab Jamun, Soya Biryani, Dahi Vada, Pizza, Veg Burger, Chicken Spring Rolls |
| **D. Needs an external blog link** for the actual method | 2/15 | Dal Makhni, Rasgulla |
| **E. Useless** — no ingredients, no steps, no blog | 3/15 | Cholle Bhature, Samosa, Jamie Oliver Pancakes |

Answering the owner's five original questions directly: full ingredient list **11/15**;
ordered steps **4/15**; any per-step duration **4/15** (the same 4 — durations only ever
show up alongside real steps); just-a-blog-link **2/15**; useless **3/15**.

### The finding that reshapes this design: bucket C, not bucket D, is the dominant failure

The brief's prior assumed two buckets — "has a usable description" and "needs the
blog-link leg." Real data has **four**, and the biggest one (**6/15, 40%**) is neither:
ingredients are present, but there is no method text *and no link to follow*. There is
nothing to redirect the LLM to. An extractor given one of these has a title, an
ingredient list, and no textual basis whatsoever for the step sequence, what runs
unattended, or how long anything takes.

This is qualitatively different from "attention was ambiguous, default conservatively."
In bucket C, the entire **cooking chain is unstated** — there is no anchor to segment
into nodes at all beyond what an ingredient's own `prep_note` licenses (COOKING_GRAPH.md
§6 already sanctions inferring a `chop_onion` node from "onion, finely chopped" — that
inference is fine, bucket or no bucket). What bucket C rules out is inventing the
**cooking** nodes: sauté, simmer, bake, combine, finish. And COOKING_GRAPH.md §5
invariant 3 requires **exactly one sink node of `kind: "finish"`, reachable from every
source** — a graph literally cannot validate without one. For bucket C there is no
textual basis for a finishing action, so **a valid `CookingGraph` cannot be honestly
constructed from these sources at all** — this isn't a policy choice to be conservative,
it's the existing invariant making the graph structurally unsatisfiable from grounded
content alone. §4.2 turns this into a hard pipeline gate (Tier 0). The owner has
ratified it: ingredients-only is useful *recovered* information — a shopping list — but
not sufficient evidence for a trustworthy `CookingGraph`, and no fake linear plan may be
manufactured from it.

Bucket D (blog-link leg) only rescues 2/15 — real, cheap, worth having, but it is not
the majority fix. Legs 1 (description) + 2 (blog JSON-LD) together reach a groundable
method for **6/15 (40%)** of this sample (buckets A+B+D). The other 60% split into
"needs a future acquisition leg" (captions/audio — bucket C, postponed) and "genuinely
nothing there" (bucket E, 20%). **M2.9's honest coverage ceiling, on this sample, is
~40%.** That is a finding to carry forward, not a shortfall to paper over — see §6 for
why this is a coverage problem, not a cost problem.

### A secondary, free signal: YouTube chapter markers

Two of the four grounded-method videos (both Sanjyot Keer / Your Food Lab) carry
creator-authored chapter timestamps in the description (`Marination 0:57`,
`Filling 2:41`, `Final process 4:36`, `Plating 6:29`, `Outro 6:49`). These are **directly
grounded** — arithmetic on stated timestamps, zero LLM inference — but they don't map
1:1 onto graph nodes: one chapter often spans several nodes, and chapters like "Intro"
or "Outro" aren't nodes at all. Treated as node-level durations they'd be wrong; treated
as a **stage-level corroboration signal** — "does the LLM's claimed node durations for
this stretch roughly match the time the creator actually spent on screen?" — they're a
legitimate, free sanity check with no inference risk.

**The distinction, stated as a rule (owner-ratified):** a chapter delta is *grounded*
data about how long the creator spent *on screen* for a stretch of the recipe. It is not
a claim about how long the *cook* will spend, and it is never written into
`Node.duration_typical`. It is captured at acquisition (§4.4), carried on
`NormalizedRecipe.chapters`, and used in exactly one place: an import-time corroboration
check that compares the sum of a stage's `duration_typical` against the matching chapter
delta and emits a warning when they diverge grossly (e.g. the model claims 25 min for a
stretch the creator showed in 90 s). An LLM-inferred duration is a *guess with a stated
basis*; a chapter delta is a *measurement of the wrong quantity*. Neither is a stated
cook time; they corroborate each other, and neither substitutes for the other.

## 1. Current architecture, as found (where a normalized recipe enters with least disturbance)

- `abc_cook/extract/` is an empty package — docstring only. No adapters, no prompts, no
  `validate.py`. The §5 invariants are specified in `COOKING_GRAPH.md` but implemented
  nowhere; `schedule()`'s own docstring says "validation is the caller's job."
- `api/routes/recipes.py` reads `tests/fixtures/*.graph.json` off disk, calls
  `schedule()`, and returns `RecipePlanResponse { graph, plan, stages }` — exactly the
  shape `derive.ts` / `PlanScreen.tsx` render. **An import that ends in a valid
  `CookingGraph` needs zero frontend changes** to reach the existing Plan view.
- `SourceRef.kind: "url" | "image" | "text"` exists; nothing branches on it today.
- `CookingPlan.warnings` is already rendered by `PlanScreen.tsx` as a bordered note
  block; `"degraded"` is already a reserved value in the schema's own docstring.
- `StageSpan` (in `plan.py`) is precedent for exactly the move this design needs: it was
  kept **out of** `CookingPlan` specifically so a rendering-only addition wouldn't force
  a rewrite of all six golden fixtures. The same reasoning is applied below to
  provenance/confidence (§5).
- `DESIGN_SYSTEM.md` § *Authored wait phrase* already flags "how do link-extracted
  imports get a caption" as a named, deferred import-pipeline decision — still deferred;
  the `attention`-derived caption remains the floor for imported recipes in M2.9.
- The scheduler's freshness mechanism (`freshness_ready` in `scheduler.py`,
  `_freshness_notes` in `safety.py`) is keyed entirely on `max_lead_min is not None`.
  A null means "no constraint." There is no way to say "constrained, magnitude
  unknown" — this matters for §4.6.
- The venv has no LLM SDK, no `yt-dlp`, no `recipe-scrapers`; only `httpx` is present.
  No `.env` exists; no provider credentials are configured anywhere on this machine
  (checked: env vars, `.env` files, `ant auth` profile, installed SDKs — §10.B).

## 2. What's reusable as-is

- The entire scheduler (`abc_cook/schedule/`) and its six-golden-fixture test harness —
  untouched. An imported graph is just another `CookingGraph` to `schedule()`.
- `RecipePlanResponse` and the `/recipes/{id}/plan` route/tests — untouched; a new route
  is added alongside, not instead (decision 3).
- The §5 invariant *list* (already fully specified in prose) — just needs `validate.py`
  written against it, which was always the import milestone's job.
- The "one LLM call per import, two only on repair" and "₹0.5–₹2 budget" rules already
  set the shape of the extraction call (§6).
- `graph.py`'s `Node`/`CookingGraph`/`Ingredient`/`SourceRef` models — untouched. No
  field is added to any of them in this design (see §5 for where provenance goes).

## 3. What's genuinely missing

Everything under `abc_cook/extract/`: acquisition, normalization, the extraction LLM
call, provenance tracking, validation, the repair loop, and the `/import` route. All of
it is new. None of it existed even as a stub beyond the package docstring.

## 4. Proposed M2.9 design

### 4.1 The pipeline and its seams

```
YouTube URL
  │
  ▼
[acquire]  yt-dlp metadata + description-link scan + chapter parse   (no LLM)
  │            └─ if a description link looks like a recipe blog →
  │               [acquire/blog] fetch + parse schema.org Recipe JSON-LD   (no LLM)
  ▼
RawAcquisition                                          (transient, extract/-internal only)
  │
  ▼
[normalize]  ONE LLM call: structure ingredients, and — only if method text
  │          exists — draft candidate graph nodes/edges/timing
  ▼
NormalizedRecipe + confidence/warnings         (real Pydantic model, schema/normalized.py)
  │
  ▼
┌─────────────────────────────────────────────────────────────────────────┐
│  [FUTURE HUMAN REVIEW / ACCEPTANCE — architectural seam, not built now] │
│  M2.9 passes straight through with no UI, no accept/reject, no         │
│  endpoint, no persistence. The seam exists because normalize.py's      │
│  output is a real, inspectable value and graph.py is a separate call — │
│  nothing here writes straight into a persisted CookingGraph.           │
└─────────────────────────────────────────────────────────────────────────┘
  │
  ▼
[graph]   NormalizedRecipe → CookingGraph | refusal      (refuses when method_grounded=False —
  │                                                        see Tier 0 below, not a bug, a gate)
  ▼
[validate]   §5 invariants — hard gate, one repair pass, else degrade (Tier 1)
  │
  ▼
CookingGraph  →  [existing scheduler]  →  CookingPlan  →  [existing Plan view]
```

This satisfies the owner's clarification directly: extraction does not write into a
persisted `CookingGraph` with no seam. `normalize.py` and `graph.py` are separate
functions with a real value (`NormalizedRecipe`) crossing between them. A future review
step intercepts exactly there — reads `method_grounded`, `warnings`, and per-field
confidence, and decides — without this document designing what it looks like, what it
persists, or how a person interacts with it. For M2.9 it is a pass-through.

### 4.2 Three outcomes, not two

The existing spec (§5) only names two: a clean scheduled plan, or a degraded linear one
after invariants fail. Step 0 shows a third case that must be distinguished, because
"linear" is not automatically "safe" — a linear plan built from **invented** steps is
just as untrustworthy as a parallel plan built from invented `attention`.

| Tier | When | What ships | Why |
|---|---|---|---|
| **0 — refuse before graph** | `method_grounded == False` (bucket C/E: no method text, no blog rescue) | No `CookingGraph`, no plan at all. `ImportResult` carries the ingredients found (still useful — a shopping list is real information) and `status: "method_not_grounded"`. | Invariant 3 (single `finish` sink) cannot be honestly satisfied — there is no textual basis for how the dish finishes. Building a graph here means inventing the entire cooking chain from dish-name world knowledge, which is exactly the "recognizable dish → hallucinated method" failure the owner ruled out. **This also means the LLM is never called for bucket C at all** — a real cost saving, not just a trust one (§6). |
| **1 — existing degrade** | Method text existed, extraction ran, but §5 invariants fail even after one repair pass | A **linear chain built from the source's own stated steps**, `plan.warnings = ["degraded"]` | The steps themselves are grounded; only the graph *structure* (parallelism) is being discarded for safety. This is the path already specified in `COOKING_GRAPH.md` §5 — unchanged. Also the fallback when §4.6's structural freshness encoding is ambiguous. |
| **1.5 — ships, but flagged** | Graph validates and schedules, but a scheduling-relevant field (`attention`, duration, dependency, freshness) was inferred rather than stated, in a way that touches a wait window | The optimized plan ships, **under the conservative behaviours in §4.7** — so the inference has already cost parallelism before the plan is built. `plan.warnings` gains a line naming what was inferred. `ImportResult.review_recommended = true`. | Owner-ratified: still probably useful, but must not be represented as equivalent to a fully source-grounded plan. The Plan view's "saves you 9 min" needs a hedge when the 9 rests on a guess. M2.9 needs the flag and the warning to exist on the response; the UI treatment is a later milestone. |

Tier 0 is the one genuinely new architectural rule this document adds to §5. Tiers 1 and
1.5 both still call the scheduler on a real graph; only Tier 0 refuses to build one.

### 4.3 `SourceKind` and `SourceRef`

YouTube imports stay `kind="url"`, `value=<the video URL>`. `SourceRef` is a 3-field
model that rides inside every persisted `CookingGraph` and is exercised by all six
golden fixtures — it is not touched, and no new enum value is added.

Cost of that choice, stated plainly: once a graph exists, `kind="url"` cannot later say
*which* acquisition leg produced it, whether chapters existed, or how confident any
field was. That richer record lives only in the transient `NormalizedRecipe` /
`ImportResult`, visible during the import flow, not persisted alongside the graph
thereafter. This is an acceptable trade — provenance is a within-import trust/debugging
signal, not something the Plan view needs later to explain why a window exists — and it
is bound up with decision 3 (§9), which the owner has now made.

### 4.4 Acquisition legs — the *first* strategy, not the final YouTube architecture

**In for M2.9 (owner-ratified):**

| Leg | What it fetches | LLM? | Rescues (Step 0) |
|---|---|---|---|
| 1. Video metadata | title, channel, description, and chapter lines parsed from the description text | no | buckets A, B |
| 2. Description-linked blog | any description URL that resolves to a page carrying `schema.org` `Recipe` JSON-LD: `recipeIngredient`, `recipeInstructions` (flat strings *or* `HowToSection` → `HowToStep`), `prepTime`/`cookTime`/`totalTime`, `recipeYield` | no | bucket D |

Both verified live in §10.A: both Step 0 blog domains carry rich, well-formed Recipe
JSON-LD. Leg 2 selection heuristic: try every description URL that is not a known
social/video/affiliate host (youtube, instagram, facebook, twitter/x, pinterest, tiktok,
amazon, bit.ly *after* resolution to one of those); follow redirects (both Step 0 links
redirect); parse every `<script type="application/ld+json">` block, walk nested
`@graph`, and take the first object whose `@type` is or contains `Recipe`. **When leg 2
finds instructions, they take precedence over the description's own method text** —
structured `HowToStep` lists are a stronger grounding than free prose, and `HowToSection`
names map almost directly onto `Stage` labels.

**Postponed, with a defined failure path:**

| Leg | Why postponed | How it slots in later |
|---|---|---|
| 3. Captions / auto-transcript | `youtube-transcript-api` works from a laptop and is blocked from cloud IP ranges; rotating residential proxies cost money; managed transcript endpoints run ~$0.30–0.60/1K. None of this can be honestly validated from a laptop, which is where M2.9 is built. | A function `acquire/transcript.py` returning the **same `RawAcquisition`** shape with `transcript: str \| None` populated. `normalize.py`'s input contract does not change; the extraction prompt gains one more grounding section. |
| 4. Audio transcription (Whisper-class) | ~$0.006/min and real latency; same validation problem. | Same shape, same seam. |

The extensibility contract, stated once: **`RawAcquisition` is the only thing
downstream sees.** It carries every field a future leg could populate (`description`,
`chapters`, `blog_recipe`, `transcript`), each nullable. Adding a leg means adding one
producer function and one prompt section — never a downstream redesign. When legs 1+2
produce no method text, the pipeline halts at Tier 0 and `ImportResult.status` says
`method_not_grounded`; that is the documented, clean failure *into* legs 3/4, and the
status value is where a later milestone attaches "try transcript."

`yt-dlp` fetches public page metadata the same way the official player does; it does
not circumvent bot protection or fetch anything a browser wouldn't. If it proves
brittle, `acquire/youtube.py` is the single file that changes when swapping to the
official YouTube Data API v3 (`videos.list`, `snippet.title`/`snippet.description`, 1
quota unit per call, 10K/day free).

### 4.5 API shape — `POST /import` returns a job; the client polls

Acquisition (~1–3 s), optional blog fetch (~1–2 s), and one LLM call (~3–10 s depending
on model and method length) put a typical import at **5–15 s**. Decision: **job id +
poll**, not a blocking request.

- `POST /import { url }` → `202 { job_id }`
- `GET /import/{job_id}` → `{ status, result?, error? }` with
  `status ∈ acquiring | extracting | validating | done | method_not_grounded | failed`

Why not block: a 15 s synchronous handler ties up a worker under any real concurrency,
Cloud Run (the target, per `CLAUDE.md`) has its own request-timeout posture, and the
three-stage status maps directly onto the tiny UI the brief specified ("Getting
recipe…" / "Extracting…" / "Building plan…"). Retrofitting polling onto a blocking
endpoint later is exactly the kind of change the owner asked to avoid.

Job store for M2.9: an in-process `dict[job_id → JobState]`, cleared on restart. This
is deliberately **not** the M5 persistence design and must not grow toward it — design
the boundary (`JobStore` protocol with `get`/`put`), implement the dict.

`App.tsx`'s existing `loading` view state (a single terminal transition) becomes a small
polling state machine for imports; the existing fixture path is untouched.

### 4.6 Freshness — `max_lead_min` null semantics (decision 5, owner-ratified)

The owner's ruling: do **not** invent a numeric `max_lead_min` from phrases like
"serve immediately" or "add just before serving." The source establishes that a
freshness constraint *exists*; it does not supply a defensible magnitude. And the two
nulls — "no constraint" and "constraint exists, magnitude unknown" — **must not collapse
to identical scheduler behaviour.**

**The limitation, stated first:** the existing scheduler cannot represent case B.
`freshness_ready` withholds a node only when `max_lead_min is not None`; `_freshness_notes`
warns only against a number. A null is, to `schedule()`, an unconstrained node that may
be packed into the earliest available window — which is exactly the unsafe outcome for
whipped cream or a cut avocado. Neither the schema nor the scheduler is changed in M2.9,
so the distinction has to live elsewhere and the scheduler has to be steered through
inputs it already understands.

**Representation (three-valued, on the normalized recipe, not on `Node`):**

```
NormalizedStep.freshness: "none" | "stated_unbounded" | "stated_numeric"
NormalizedStep.freshness_cue: str | None      # the source phrase, verbatim
NormalizedStep.max_lead_min: int | None       # populated only for stated_numeric
```

Carried into `GraphProvenance` per node. `CookingGraph.max_lead_min` is a number only
for `stated_numeric`; null for both `none` and `stated_unbounded` — the schema can't say
more, and the doc doesn't pretend it can.

**Scheduler steering for `stated_unbounded` — the chosen safe degradation:**

`graph.py` encodes the stated *ordering* constraint structurally. "Just before X" means
"after everything else X needs." So the fresh node's `depends_on` is extended with every
other non-fresh dependency of its consumer. This is not an invented edge — it is the
literal dependency content of the source phrase, and it is exactly the withholding rule
`freshness_ready` already implements dynamically (`scheduler.py:123-140`), expressed
statically in the graph instead. Effect: the node structurally cannot start until its
consumer is otherwise ready, so it runs just-in-time and cannot land in any earlier
window. Provenance marks those edges `inferred` (derived from a stated constraint).

What this does *not* give, and how each gap is covered:

| Gap | Cover |
|---|---|
| No post-hoc lead warning (needs a number) | An **import-time** warning is always emitted for every `stated_unbounded` node: *"`whip_cream` must be made fresh (source: 'serve immediately'); no time limit is stated, so it is scheduled right before `assemble`."* `review_recommended = true`. |
| Consumer can't be identified, or the node has ≠ 1 consumer | Structural encoding is ambiguous → the recipe degrades to **Tier 1 linear**. Safest available; mirrors the scheduler's own single-consumer scope for numeric freshness (§4.5 of `COOKING_GRAPH.md`). |
| Consumer still delayed by cook contention after the fresh node finishes | Same residual risk the existing numeric path has (`test_freshness_warning_fires_when_consumer_is_delayed`), minus the warning. Accepted for M2.9; closed by the enhancement below. |
| The Map view draws the extra derived edges | Cosmetic. They are true dependencies of the stated recipe; noted so nobody reads them as a rendering bug. |

**Recommended post-M2.9 enhancement (not in scope, needs its own approval):** let the
schema say `max_lead_min: int | Literal["unbounded"]` (or a `freshness_sensitive: bool`),
so `freshness_ready` withholds on either form and `_freshness_notes` warns on *any*
positive lead for the unbounded form. That touches `schema/node.py`, the scheduler, and
the goldens — precisely the change class this milestone is forbidden from making, which
is why the structural encoding above is the M2.9 answer.

### 4.7 Tier 1.5 — what "conservative scheduling behaviour" concretely means (decision 6)

An inferred field must not create an unjustifiably aggressive optimization. Per
scheduling-relevant field, the rule that makes inference cost parallelism *before* the
scheduler runs:

| Inferred field | Aggressive direction (forbidden) | Conservative behaviour (required) | Sets `review_recommended`? |
|---|---|---|---|
| `attention` | Inferring `periodic`/`unattended` → creates a window | Never inferred toward a window. No cue → `hands_on`. Inferred attention is therefore *always* `hands_on` and creates no window. | No — nothing to review; parallelism was simply not claimed |
| Duration of a **window host** (vague text, §6 of `COOKING_GRAPH.md`) | Setting `duration_typical` high → large `capacity_min` → many tasks packed | `duration_typical` is set to the **low end** of the plausible range (`duration_min == duration_typical`), `duration_max` to the honest upper bound. Smaller capacity → fewer/shorter tasks pass the packing and `duration_max` gates. The displayed number is explicitly "typical" and the `doneness_cue` governs the actual finish. | **Yes** — the window exists on an estimated size |
| Duration of a non-host node | Under-estimating → task packed into a window it may overrun | Estimate honestly; `duration_max` honest. The `duration_max` eligibility gate (§4.4 of `COOKING_GRAPH.md`) already protects the window. | Only if the node was window-claimed |
| `depends_on` | Dropping an edge → two steps deemed independent → one may run in a window | **Legacy (`depends_on_previous`, every `depends_on_steps` null):** consecutive stated steps get the sequential edge **by default**. Independence is asserted only when *both* hold: no shared ingredient/component, and neither consumes the other's `produces`. **Explicit (`depends_on_steps` stated on any step, CP2):** a claim names earlier steps; `[]` claims none, null means "not provided" and gets the previous step. The builder only **adds** edges: invalid indices are dropped (a claim left empty falls back to the previous step); producer→consumer edges; the *descendant closure* (the continuation of a claimed step's work is included, stopping at a step whose named product a later step consumes); the §4.7 test run pairwise against **every** earlier step not already reached; the nearest earlier step on the same `burner`/`oven`; and any required node left with nothing after it is joined into the finish. **Both paths:** a shared pantry staple (salt, water, oil, whole-word match) is not a shared ingredient; a produced component is never a staple, and a produces/consumes link is never exempt. | **Yes**, if a window-claimed task's eligibility depended on an inferred independence; on the explicit path, whenever a guard edge (pairwise, heat station, sink join) or a fallback was added |
| Freshness (`stated_unbounded`) | Null → node packed early | §4.6 structural encoding | **Yes**, always |
| `interruptible` | `True` → task may use a `periodic` window's full capacity | `False` when uncertain → 3-min cap applies in `periodic` windows | No |
| `station` (cooking verb, station unknown) | `none` → unbounded, two heat nodes overlap silently, no `uses N burners` note | `burner` for heat verbs (fry/sauté/simmer/boil/heat), `oven` for bake/roast, `counter` for hands-on prep, `none` only for genuinely resource-free waits (rise, soak, cool, macerate — matching the goldens), `fridge` only when stated | No — contention is a warning, not a window |

**Optional and alternative instructions (CP2).** A step the extraction marks
`optional`/`alternative` is kept out of the mandatory graph only when its `role_cue` is a
verbatim source substring **and** carries a marker from a closed list ("if you", "if
desired", "optional", "alternatively", "instead", "or you can", "method:"). It then
becomes no node: its verbatim text is appended to the `tip` of the step it modifies as
`Optional: …` / `Alternative: …`, never deleted, and ingredients only it uses are marked
`optional`. An unverified claim stays a required step and sets `review_recommended`. If
every step would become a note, all stay required. The finish sink is the last
*required* step.

The composite rule: `review_recommended` is set whenever **a wait window's existence,
size, or membership rests on an inferred value.** A plan whose every window is built from
stated attention, stated durations, and stated order is *not* flagged, even if cosmetic
fields (`kind`, `cuisine`, `servings`) were inferred.

## 5. The extracted / inferred / forbidden field table

Three categories, per the owner's request, applied field by field. **"Forbidden" is not
a style preference — it is what Tier 0 exists to enforce.**

| Field | Directly grounded when | Safely inferred (bounded) | Forbidden | M2.9 conservative default |
|---|---|---|---|---|
| `Ingredient.name/qty/unit` | Listed verbatim in description or blog JSON-LD | Unit-string normalization only | Inventing an ingredient not mentioned anywhere | — |
| `Ingredient.prep_note` → prep-node existence | Stated on the ingredient line ("finely chopped") | A `chop_x` prep node from that note alone, per §6 — already sanctioned, not new | A prep node with no ingredient-note or method-text basis | — |
| Node existence (cooking chain) | Method text describes a discrete action | Splitting one written step into multiple nodes when attention changes (§6) | **Any cooking node (sauté/simmer/bake/combine/finish) not implied by method text** | Tier 0: refuse graph construction entirely |
| `Node.attention` | Explicit cue word/phrase ("simmer covered", "stir occasionally" → periodic; "let rise", "marinate", "preheat" → unattended) | — (there is no bounded middle ground here) | **Inferring `periodic`/`unattended` from dish-type world knowledge with no textual cue** — this is the false-parallelism risk itself | `hands_on` whenever no cue is present, full stop, regardless of how "obviously" a dish simmers |
| `Node.kind` | Verb-derived (sauté→active, bake→passive, mix→combine, chop→prep) | Same, when verb is slightly ambiguous | — (low risk: `kind` never drives scheduling, §4 of COOKING_GRAPH.md) | `active` if genuinely ambiguous |
| `Node.duration_typical/min/max` | Stated number in text; chapter-delta corroboration (§0) | A plausible typical from cuisine convention **only** when the text itself is vague-but-present ("cook until golden") — §6's existing rule, widen min/max, fill `doneness_cue`; **for a window host, typical = low end** (§4.7) | Inventing a duration for an action that was itself invented; writing a chapter delta into a node duration | N/A when node doesn't exist (Tier 0) |
| `Node.depends_on` | Explicit connective ("then", "once X, add Y"); JSON-LD instruction order; chapter order; a stated freshness phrase (§4.6); an extracted `depends_on_steps` claim, verified (§4.7) | Consecutive-step sequential edge by default; independence only under §4.7's two-condition test (shared pantry staples exempt). Explicit claims are extended, never trimmed, by producer edges, the descendant closure, pairwise verification, the same-heat-station guard and the sink join (§4.7) | Inventing an edge with no order, ingredient, or stated-constraint basis; removing an extracted dependency; turning an unverified optional/alternative claim into a missing step | Sequential; a null `depends_on_steps` on the explicit path → the previous step |
| `Node.station` | Explicit ("in the oven", "on the pan", "in the fridge") | Verb→station lookup (§4.7) | — | `burner` for an unknown heat verb; `none` only for resource-free waits |
| `Node.interruptible` | Almost never stated explicitly | From `kind` (prep→true, active/finish→false, matching all six golden fixtures) | — | **`False` when uncertain** |
| `Node.max_lead_min` | A stated **number** ("use within 10 minutes") | — | **Any number not stated by the source**, including a "conservative" 0–2 min for phrases like "serve immediately" (owner decision 5) | `null`; the constraint's *existence* is preserved as `freshness: "stated_unbounded"` + `freshness_cue`, and steered structurally (§4.6) |
| `Node.doneness_cue` | A qualitative phrase is textually present ("until golden") | Lightly rephrasing that same stated phrase | Inventing a cue with no textual basis at all | `null` |
| `CookingGraph.stated_total_min` | Explicit "total time" claim in text or blog JSON-LD `totalTime` | — | **Populating from raw video duration** — that includes talking and editing, not cook time | `null` |
| `CookingGraph.servings` | Explicit "serves N" / JSON-LD `recipeYield` | Default to 4 (owner decision 4) when absent | — | `4`, flagged `defaulted` in provenance — informational only, does not gate graph construction |
| `CookingGraph.cuisine` | Explicit or channel/title cue | Best-guess from channel/title | — | `null` if no basis — cosmetic field only |

**Forbidden-assumptions summary (the short version):**

1. Never invent a cooking node with no method-text basis.
2. Never infer `periodic`/`unattended` attention without an explicit textual cue.
3. Never invent a duration for a node that was itself invented.
4. Never invent a dependency edge with no stated order, ingredient, or constraint basis.
5. Never populate `stated_total_min` from video runtime.
6. Never invent a `doneness_cue` with no textual anchor.
7. Never invent a `max_lead_min` number; never write a chapter delta into a node duration.

### Where confidence/provenance lives

Not on `Node` — that would touch `schema/node.py`, all six golden fixtures, the
extraction prompt, and a new invariant, exactly the cost `DESIGN_SYSTEM.md` § *Authored
wait phrase* already flags for a similar-shaped addition. Instead, a **sibling record**,
`GraphProvenance` (new model, `schema/normalized.py`): `node_id → {field_name:
"extracted" | "inferred" | "defaulted"}`, plus the per-node `freshness` triple from
§4.6, computed by `provenance.py` alongside `graph.py`'s output — the same pattern
`StageSpan` already established for plan-adjacent, non-schema-critical data.

Consequences: golden fixtures need no provenance field (nothing applies to
hand-authored graphs); the scheduler never sees or needs it; a later milestone can join
it onto the Plan view for a confidence indicator exactly the way `derive.ts` already
joins graph+plan+stages, without this milestone building that UI. A `defaulted`
`attention` (i.e. `hands_on` because no cue existed) is thereby distinguishable from an
`extracted` `hands_on` — the distinction the owner asked for in decision 3's clarification.

### 6.2 Recommendation

**Anthropic, `claude-haiku-4-5` for the single extraction call; `claude-sonnet-5` for
the repair pass only.** Rationale, in order:

1. The pipeline's contract *is* Pydantic. Anthropic's structured outputs parse directly
   against `NormalizedRecipe` — no hand-written JSON parsing layer, no schema drift
   between what the model is asked for and what `validate.py` checks.
2. Comfortably inside budget with room for the repair pass, and the cheap→escalate split
   is exactly what `COOKING_GRAPH.md` §6 prescribes ("start with a cheap model, escalate
   only on repair").
3. Reversible: the adapter boundary means Gemini Flash is a one-file swap if
   verification B shows Haiku's multi-script accuracy is inadequate. Gemini 2.5 Flash is
   the named second option, and the cheapest.

This is a recommendation, not a fait accompli — the owner sets up billing, and if that
billing is Google's, the adapter is written for Gemini first and the reasoning above
still holds. What is *not* recommended is hard-coding any provider in a route or in
`normalize.py`.

SDK/dependency implications: `anthropic` (Python 1.x) added to `pyproject.toml`
`dependencies`; `pydantic` already present. Haiku 4.5 needs no thinking for this task;
if Sonnet 5 is used for repair, adaptive thinking at `effort: "low"` is the right
setting. No vision, no tools, no streaming needed at these output sizes.

### 6.3 Cost per *successful* import, weighted by Step 0

- **method_grounded successes (40% of raw attempts, buckets A+B+D):** ≈1.15 calls each →
  **≈ ₹1 on Haiku 4.5**, well under ₹2, even with every repair pass on Sonnet 5.
- **method_not_grounded (60%, buckets C+E):** **Tier 0 never calls the LLM** — ₹0

- **Expensive acquisition paths:** none exist in M2.9. Legs 3/4, when they arrive, add

**The real constraint M2.9 surfaces is coverage (~40% on this small sample), not cost.**
This echoes `PRODUCT.md`'s own line — "LLM cost is not the risk in this business."

### 10.C Verification B — actually run, 2026-09-13, provider now configured

Owner set up Anthropic billing; `apps/api/.env` populated with

instructions. Five inputs, re-fetched live via `yt-dlp` from the owner's original 15
URLs: Pakoda Kadhi (Devanagari, bucket A), Donuts (English, bucket A), Pizza (Bengali,
bucket C), Aloo Tikki Veg Burger (transliterated Hindi, bucket C), Rasgulla (Gujarati
source video, routed through the blog JSON-LD leg — same page verified live in §10.A).
7 total calls (2 truncation retries, see finding 5). Total spend ≈ ₹10–12.

**Ingredient-structuring accuracy: strong across all four scripts.** Devanagari
(Pakoda Kadhi: 15/15 ingredients, quantities and units intact), Bengali (Pizza: 12/12,
correctly parsed from a bilingual Bengali/English line and normalized to English),
transliterated Hindi (Aloo Tikki Burger: terms like "garam masala powder", "kashmiri
mirch powder" preserved and legible), and the Rasgulla blog path (7/7 ingredients, all
26 `HowToStep`s captured with their stated durations). Decision 7 (provider) holds on
this axis.

**Five concrete findings — each observed, not hypothesized — that change *how* the
pipeline must be built, though not *what* it should do (the design's rules were already
correct; the trust model for enforcing them was not):**

1. **Tier 0 self-contradiction.** For Aloo Tikki Burger (bucket C, ingredients-only, no
   method text), the model's own free-text `notes` field said *"Source provides only an
   ingredient list with no method/procedure text. method_grounded set to false"* — but
   the `method_grounded` field it actually returned was `true` (with `steps: []`). The
   model's reasoning was correct; the structured field it emitted was wrong. This is
   direct evidence for why §8.1 already requires `graph.py` to "refuse even if a future
   caller forgets the gate": that is not defensive hardening, it is load-bearing. **The
   Tier 0 gate must check `if not steps: refuse` in code, independent of whatever
   `method_grounded` the model claims.**
2. **`attention_source: "stated"` is not trustworthy.** In Pakoda Kadhi, two steps
   ("Heat about 100 grams of oil in the pan…", "Put 1 tbsp of oil in a pan and heat
   it") came back `attention: "unattended", attention_source: "stated"` with no
   explicit unattended cue in the source text — exactly the false-parallelism failure
   §5 exists to forbid. The model's own honesty flag did not catch its own violation.
3. **Freshness over-triggers on the bare word "serve."** The same recipe's closing step
   ("Serve it with rice or roti…") came back `freshness: "stated_unbounded",
   freshness_cue: "Serve"` — but plain "serve" carries no immediacy constraint the way
   "serve immediately" or "add just before serving" does.
4. **§4.7's window-host duration-clamp ("typical = low end when inferred") is not
   self-enforcing from prompt text alone.** One inferred-duration `unattended` step
   returned `duration_typical: 2, duration_min: 1` — typical should equal min. Small
   sample, but it shows the rule needs a deterministic clamp, not just an instruction.
5. **Output-token truncation, not invariant failure, was today's actual repair
   trigger.** 2 of 5 calls (Pakoda Kadhi, Rasgulla) silently truncated mid-JSON at
   `max_tokens=4000` and needed a re-run at `6000` to parse — both landed near 4800
   output tokens, well above §6.1's ~1.5K assumption. This hits precisely the richest
   bucket-A/D inputs (the ones the moat depends on), and silently doubles cost when it
   fires. It is a distinct failure mode from the invariants-failed repair pass in §6/§9
   decision 1, and needs its own always-retry handling in the adapter, not folded into
   the same one-repair-pass budget.

**The rule this verification adds, binding on the `graph.py`/`normalize.py`
implementation (§12 step 9):**

> No scheduling-relevant boolean or classification the LLM emits — `method_grounded`,
> `attention`, `attention_source`, `duration_source`, `freshness` — may be trusted as
> emitted. Each must be either (a) recomputed independently in code from the raw source
> text or the step list itself, or (b) treated only as a hint a deterministic check then
> confirms or overrides. This was always implicit in Tier 0's "refuse even if a future
> caller forgets the gate" language and in §4.7's conservative-defaults table;
> Verification B shows it is not optional hardening but a correctness requirement — in
> the one case that mattered (Aloo Tikki Burger), the model's own prose reasoning was
> right while the structured field it emitted was wrong.

**§6.3 cost revision (provisional, needs the real §8.3 eval to confirm):** a detailed
bucket-A/D recipe's realistic cost is closer to the ₹1.96 "at the edge" figure than the
₹0.98 "2× headroom" figure §6.1 gave Haiku 4.5, once output tokens are sized honestly
(~5K, not ~1.5K) — before accounting for a truncation retry doubling it further in the
worst case. Recommend `max_tokens: 6000–8000` in the real adapter (§7,
`adapters/anthropic.py`). Does not change the provider recommendation, only the budget
headroom claim.
