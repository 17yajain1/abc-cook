## Headline

1. **The linear degrade is caused by invariant 8 (`stated_total_min` ±40%), which the repair pass is structurally incapable of fixing.** Both successes, and every one of the five recorded Dal Makhni repair runs, carried it. Even a *perfect* repair proposal degrades while it is present (proven, §E). The repair pass has therefore **never been allowed to succeed on a real recipe** — its quality is unmeasured, not bad.
2. **Checkpoint 2 under-reported cost.** The ₹3.29 / ₹2.87 figures came from a side script that made only the extraction call. The real pipeline also fired the Sonnet repair call on both imports (≈ ₹2.0–2.7 each, estimate — uninstrumented) and then threw its result away. True cost was ≈ ₹5–6 per import, for a plan with `saved_min = 0`.
3. **Output tokens are 76–79% of extraction spend, and ~55–65% of output tokens are JSON scaffolding** (indentation, key names, `null`/default fields, `notes`), not grounded content. That is where the ₹2 comes back from.
4. **Truncation retries are the single largest waste.** `normalize.py` retries a `max_tokens` truncation with identical inputs and the same cap, so every Ramen import burned 2 × ₹4.15 for nothing. Across s17, ≥ 9 truncated Ramen calls ≈ ₹39 wasted.
5. **The cheap-path reference the owner asked for does not exist in instrumented form.** No blog/description import has ever been run with token counts through the full pipeline. The closest (Dal Makhni, M2.9 s15) is an *estimated* ₹2.3 extraction + a Sonnet repair, and it degraded too.

## D. Token-cap strategy

`max_tokens` is a ceiling, not a charge. Below-safe-ceiling caps are justified only by runaway protection and SDK limits.

- **Default 16,000** (not 8K/12K). Covers 46 steps × ~300 + header. Justification for not going straight to 32K: worst-case loss on a runaway generation is ₹6.8 not ₹13.6, and the Python SDK refuses non-streaming requests whose `max_tokens` implies > 10 min (threshold ≈ 21K tokens) — 32K needs `.stream()` or an explicit timeout.
- **On `stop_reason == max_tokens`:** do **not** retry at the same cap (B.8). Inspect the truncated text: if it contains the same step `text` ≥ 3 times, or `"steps"` is missing after 16K tokens, treat as runaway → stop, Tier 0, warning `"truncated"`. Otherwise **one** re-call at 32,000 via streaming. A second `max_tokens` → stop.
- **On unparseable (not truncated):** keep the one identical retry — that is what sampling variance can fix.
- **12K-works-sometimes is sampling variance:** Ramen's 46-step output lands either side of 12K by ±10%; no fixed number between 12K and 14K is safe. 16K default + 32K escalation makes the number irrelevant.
- **Repair call:** keep 8K with `effort="low"` (measured to complete well under it). Unchanged.
- **Truncation rate** becomes a metric (§Metrics); if it is > 0 at 16K on real traffic, the default moves, not the escalation.

## E. Root cause of the linear degrade (the highest-value item)

**Finding: invariant 8 — `stated_total_min` ±40% — fires deterministically on these recipes and cannot be fixed by the repair pass, so `repair_or_degrade` always falls through to `build_linear_graph`.** Not graph size, not a timeout, not a node-count threshold, not cycle detection.

### The chain, with the specific branch

1. Sabudana's title/description says "30 min"; Shahi Tukda's says "सिर्फ़ 15 मिनट में"; Dal Makhni's blog says 65 min. The prompt tells the model `stated_total_min` is "only an explicit total-time claim" — so it extracts 30 / 15 / 65. Correct per prompt.
2. The same sources ground a 2-hour soak (Sabudana), a 1-hour fridge set (Shahi), a 3-hour soak (Dal). These are real, cue-verified, stated durations. Serial sums: 152–156 / 140–220 / 262 min.
3. `validate._check_stated_total` (`validate.py:277`): `|serial − stated| > 0.4 × stated` → `Violation("stated_total_min")`. Allowed drift is 12 / 6 / 26 min. **Fires every time** — confirmed by the `"Dropped the source's stated total time"` warning present on every one of the ~9 successful runs in s17 and all five Dal Makhni repair runs.
4. `import_pipeline.py:122` → `repair_or_degrade`. The Sonnet call runs (₹2+). `RepairProposal` can only set `consumes_ingredients` / `produces_component` / `depends_on_previous` (`repair.py:54–70`, by design). It cannot touch durations or `stated_total_min`.
5. `repair.py:245–246`: `candidate = build_graph(repaired_recipe, …)`; `if candidate.graph is not None and not validate(candidate.graph)` — `validate` still returns the `stated_total_min` violation → **condition False** → falls to `repair.py:255` `build_linear_graph(...)`.
6. `graph.py:493–510`: only in `force_linear` mode does `build_graph` drop the unsupportable `stated_total_min` (with the warning we see). Linear chain → every node depends on its predecessor → `scheduler.py:216–224` finds no hands-on node inside any host interval → windows empty → dropped at `scheduler.py:244` → `saved_min = 0.0`.

### Proof (offline, no LLM, run today against the frozen Dal Makhni fixture)

| Case | `validate()` | `repair_or_degrade` outcome | Plan |
|---|---|---|---|
| As extracted | sink ×1, produces ×3, **stated_total** | — | — |
| As extracted, `stated_total_min=None` | sink ×1, produces ×3 | — | — |
| Hand-perfect repair, stated_total kept | **stated_total only** | fake adapter returning that perfect proposal → **`degraded`** | linear, saved 0 |
| Same perfect repair, stated_total dropped | none | same proposal → **`repaired`** | total 245 / serial 262 / **saved 17, 1 window with 4 tasks** |

So: with the assertion dropped the *same* repair proposal succeeds. The repair pass has never had the chance to succeed on real data; every recorded "degraded" is explained by this branch. Whether the *real* Sonnet proposals would have validated is unknown — that is the first thing to measure once the gate is fixed (H.T1).

### What "fix" means, and the product decision inside it

`build_graph` in non-linear mode should do what it already does in linear mode: drop `stated_total_min` (never invent a number to close the gap), add the warning, set `review_recommended=True`. Invariant 8 then becomes unreachable from `build_graph` output — the same status invariant 7 already has via `_resolve_duration`'s clamp. `validate.py` and `COOKING_GRAPH.md §5` are unchanged; the invariant still guards hand-authored graphs and the goldens.

The product decision the owner should make consciously: invariant 8's stated purpose is "the model invented or dropped work." On real sources it fires almost exclusively on **marketing titles vs. long passive steps** ("15 minutes" videos with a 1-hour set). Two options: (a) drop the assertion as above (recommended — it is already the sanctioned behaviour in linear mode); (b) exclude `unattended` nodes from the serial sum before comparing (closer to what "15 min" means colloquially, but a new rule). (a) is a 6-line move of an existing block; (b) is new product logic.

### A second, smaller cause to watch (not yet observed, but predictable)

After the fix, the remaining violations on these graphs are structural (`single_finish_sink`, dangling `produces`) and *are* what the repair pass exists for. But a repaired-and-valid graph is not necessarily physically right: when I applied a conservative deterministic repair (dangling produces → None, extra sinks → finish) to Dal Makhni it validated and scheduled a window — with "brown the garlic and add it straight to the boiling dal" placed at minute 0, three hours before the dal exists, because the model never wrote the consumes link back to the dal. `depends_on_previous` only encodes the immediate predecessor; a branch that rejoins needs the produces/consumes link the model often omits. **Windows > 0 is necessary but not sufficient.** Metric #10 below (dangling-branch count) is the detector.

## Metrics to instrument (specification only — not built)

Hook points, in pipeline order:

| Hook | What is captured |
|---|---|
| `adapters/base.py::ExtractResult` | new `usage: CallUsage | None` — `model`, `input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`, `stop_reason`, `latency_ms`, `max_tokens_requested`, `attempt` |
| `adapters/anthropic.py::extract` | fill it from `message.usage` / `stop_reason` on every call including truncated ones; on truncation also return the partial text (needed by D's runaway check) |
| `normalize.py::NormalizeOutcome` | `calls: list[CallUsage]`, `escalated: bool`, `truncations: int` |
| `import_pipeline.py` after `validate()` | `violations_pre_repair: list[rule]` — **this is the missing datum behind §E; today it is discarded** |
| `repair.py::RepairOutcome` | `calls`, `tier`, `violations_post_repair` |
| `import_pipeline.py` return | `ImportTelemetry` on `ImportResult` (or a structured log line keyed by job id): all calls, `cost_inr` from a price-table constant (never from the provider), `tier` ∈ {tier0, clean, repaired, degraded}, `windows`, `saved_min`, `dangling_branches`, `sources`, `transcript_tokens`, `step_count` |
| `api/routes/import_.py` | one JSON log line per job; aggregates are computed offline (eval script), not in the request path |

Derived metrics (over the log):

1. cost per import (all calls)
2. cost per successful grounded import (`status == done`)
3. avg / median / max cost
4. retry rate (calls > 1) and escalation rate (ceiling raised)
5. tokens in / out, separately, per model
6. token-cap truncation rate (`stop_reason == max_tokens` / calls)
7. % imports requiring escalation
8. % producing ≥ 1 valid parallel-task window (`windows > 0` and `saved_min > 0`)
9. **cost per successful import with parallel scheduling** = Σ cost / count(done ∧ windows > 0) — the target
10. dangling-branch count per plan (branches that rejoin only at the finish node) — the "valid but wrong" detector from §E
11. violations by rule, pre- and post-repair — tells us what the repair pass is actually for
