**Session Name:** s6 · M2.5 — Direction 3 + DESIGN_SYSTEM.md hardening

## Outcome

M2.5's first visual pass (the Timetable Plan retone from s5) was **rejected by the owner
as too cold, flat and document-like** — "why it is looking terrible bed." It technically
followed the brief and still missed the quality bar. This session reset the Plan-view
visual direction, chose a new one, stress-tested it against inputs the golden fixtures
can't produce, and then did a targeted documentation pass so the eventual implementation
can't silently invent product decisions.

**No application code, no tokens, no `derive.ts`, no scheduler touched this session.**
Everything is static studies in `docs/design/` plus a documentation pass on
`docs/DESIGN_SYSTEM.md`.

**Nothing is implemented yet.** M2.5 is still open. The next session starts from the
owner's verdict on Direction 3 and its calibration.

## What happened

### 1. The Timetable Plan retone was a failed iteration

The owner reviewed the s5 result against the M2 baseline, the Figma Make design, and a
"Design B" reference (a warm, well-spaced competitor screen). Diagnosis, agreed:

- The brief's three principles were all **subtractive** ("measured not labelled", "one
  signal colour", "absence has a shape") — none told the implementation what to *add*, so
  faithful execution converged on a document.
- Signal was rationed to **zero** — the one warm mark never appeared on screen. Muted
  stage tints only work as a supporting cast for a signal that is present.
- Ground-to-field contrast was ~4% — the wait window, the most important region, did its
  work with a 4% shift and a hairline, and disappeared.
- The type scale compressed instead of expanding; the largest element on screen was a
  disabled CTA.

The register error underneath: the Map is an instrument looked at for ten seconds; the
Plan is held for forty minutes at a stove. s5 applied one register's austerity to both.

### 2. Three new directions proposed; the owner chose Direction 3

| Direction | One-sentence idea | Verdict |
|---|---|---|
| **The Hearth** | The plan is organised around the pan: one continuous thread shows what's on the heat, and your work attaches to it. | Safest, least distinctive. |
| **The Margin** | Work you can do while something cooks is set in the margin *beside* it, not underneath. | Highest ceiling; **rejected** — a ~150px margin column truncates real imported task names at 390px, plus a ~50KB serif font cost. Revisit later if Direction 3's field proves limiting. |
| **Two Kinds of Minute** *(chosen)* | Every minute is either a minute the dish needs your hands or a minute it doesn't, and the whole screen is built out of that alternation. | **Chosen.** The product insight *is* the layout; no component explaining a concept. No new font. Both risks testable in one screenshot. |

Governing decision that follows: **stage identity in the Plan is carried by ordinal +
type + whitespace, not by hue** — every direction needed its one semantic colour kept
exclusive, and a per-stage hue competes with it. Stage tints survive only in the Map,
where they carry bar fills. (Owner picked option (i): no stage hue in the Plan.)

### 3. The zebra rule — stated and validated before building

The risk that could sink Direction 3: a recipe with many unattended stretches becomes a
stripe of full-bleed fields. Resolved by construction:

> **The field is keyed to a scheduler-declared wait window (`plan.windows`), never to
> `attention`.** The scheduler only creates a window where it actually placed borrowed
> work.

A window earns the full-bleed field when **all four** hold: it exists in `plan.windows`;
`capacity_min ≥ 8`; `tasks.length ≥ 1`; `used_min ≥ 3`. Plus: adjacent qualifying windows
merge; hard cap of three per screen, lowest `used_min` demote to inline. **All
presentation-layer — no scheduler change.**

Held against every fixture — **maximum one field per screen across the entire set:**

| Fixture | Windows | Fields | Note |
|---|---|---|---|
| kadai-paneer | w1 (9 / 3 / 9) | 1 | the hero case |
| homemade-donuts | w1 (54 / 1 / 3) | 1 | sits exactly on the `used_min ≥ 3` boundary |
| chicken-biryani | w1 (18/4/11), w2 (9/1/2) | 1 | w2 demoted by `used_min ≥ 3` → inline |
| strawberry-shortcake | w1 (16/1/5) | 1 | qualifies |
| maggi-2min | none | 0 | plain list, no empty box |

Stripes are not reachable on real fixture data. Donuts turned out to be the *cavernous*
case (60-min window, one task), not the stripe case.

### 5. The 7 owner fixes (rev 1 → rev 2 of the Donuts study)

1. *(process)* fixes first, then Kadai Paneer render.
2. **Field subject line = task name only.** Dropped "1 hr" next to "60" — stating the
   same duration twice in two units weakened the numeral.
3. **Estimated stage figures flagged, not fixed** — Donuts has no `StageSpan` fixture on
   the web side; Kadai Paneer's figures are real.
4. **Slack copy kept provisional** — one line has to serve both "3 min spare" (KP) and
   "51 min spare" (Donuts); wording waits on seeing both rendered.
5. **"Rise" is no longer stranded.** When a stage's only content is a hosted field (host
   pulled out, nothing left inline), **the field absorbs the stage header.** Rule must
   apply generally, not per-case — caught again in stress study B.
6. **The tan edge marks on bare unattended rows are gone.** They implied a system that
   wasn't there (same failure class as the Map's old right-angle bracket). Proof donuts
   and Heat oil are ordinary rows. Open: non-windowed unattended time now has no visual
   distinction at all.
7. **Slack copy retoned** from shortfall ("that is the only job in the hour") to
   permission ("nothing else to do until the dough doubles"). Still provisional.

### 6. Systems robustness analysis — is Direction 3 a system or five hand-fitted screens?

The five golden fixtures were authored to be well-behaved. The primary real input path is
a YouTube/Instagram link parsed into a plan. Honest read: **Direction 3 is ~70% a system,
30% fitted to well-behaved fixtures.** Three implementation obligations the fixtures hid,
and two things to write honestly rather than overclaim:

| Case tested | Result |
|---|---|
| **Long task names** (40–90 chars) | Duration column holds on every wrapped row **once `overflow-wrap: anywhere` is added** to name fields — that CSS is not in the shipped components. Without it, a single long token overflows and shoves the duration off-screen. |
| **A 10+ task stage** | A genuine wall. **No collapse mechanism in the Direction 3 study** — needs the shipped `StageCard` collapse behaviour carried forward. |
| **No doneness cues at all** | Degrades to a plain but functional list; the field still carries the distinctive load. |
| **Field far down a long scroll** | Weakens. Partial mitigation exists (the header pre-announces the saving); 5 screens between promise and payoff is too far. |
| **No parallelism, 40-min sequential** | `saved_min == 0` → no promise line, no field, no big number. A warm typeset list — differentiation is craft, not concept. **Owner should measure** what fraction of real imports produce `saved_min == 0`. |
| **Multiple qualifying windows** | **Two 44px numbers on one screen** — punctures "the one big number in the product". Reads better than feared (different stages, different scroll positions), but the principle must be restated as "one large number *per window*". Zebra rules 5 (merge) and 6 (cap) are still untested logic — recommend shipping "one field per window, no merge, no cap" for M2.5 and deferring merge/cap to M2.75. |
| **Thresholds `capacity_min ≥ 8`, `used_min ≥ 3`** | Both are placeholders that "felt right"; low confidence. The deeper problem is the **cliff** — a hard binary (field vs inline list) at a single capacity number makes two recipes 2 minutes apart look completely different. Recommend: write both as provisional, calibrate against a real corpus in M2.75; the eventual fix may be "field always, prominence scales". |

### 7. Targeted documentation pass on `DESIGN_SYSTEM.md`

Documentation only — no code, no tokens, no component redesign, no commit at the time.
Goal: make the doc unambiguous enough that a future session can implement M2.5 without
inventing product/design decisions. Ten changes:

1. **New `## M2.5 sign-off blocker`** near the top — the `2 + 7 ≠ 12` wait-window
   arithmetic, moved out of "Still open". States it is a scheduler/product-contract
   problem, not visual copy; copy must not be reworded to conceal it; M2.5 is not signed
   off until it's resolved. Cites `COOKING_GRAPH.md` § 3 (header = `used_min` + host
   `duration_typical`) and § 4.3 (the `×0.9` / `×0.75` capacity gating that opens the
   gap) as where the *primitives* are defined — and states that **no document defines how
   the header and footer reconcile in one view**. Example left unreconciled on purpose.
   "Still open" item 1 is now a pointer; `WaitWindowBlock` got a callout.
2. **`### Register` rewritten** into a **frozen vs unresolved** split. Frozen for M2.5:
   vertical stage-row experience, not a Gantt chart, no time axis; inherits
   palette/type/radius/rule-weight/duration-column; wait windows attached to host stage;
   Map grammar does not auto-transfer. Unresolved: only the *degree* of warmth/austerity
   — a tuning question, not licence to change information architecture.
3. **Signal rule rewritten** around priority, not count: signal is reserved for the
   highest-priority constraint/action on the screen; multiple elements only if the same
   priority; never emphasis/category/selection/interactivity. Added a worked example
   table (CTA / stage tint / ink coexisting). Palette unchanged.
4. **Four `## Future Milestone Reference (M2.75/M3) — not part of M2.5 implementation`
   fences** over: connector language; StageCard `active`/`complete`; timer digits +
   behaviour; Map entry animation + task-complete motion. (StageCard-states and timer
   share one fence as two `###` rather than near-identical adjacent headers — flagged for
   the owner to split if wanted.) Nothing removed.
5. **Stage-colour accessibility validation** added: test protanopia / deuteranopia /
   tritanopia / greyscale. Pass condition is "stage colour is never the sole carrier of
   identity", not "tints stay distinct". Do not raise saturation pre-emptively.
6. **`--color-signal-sunk` removed from the M2.5 token set** — confirmed zero consumers
   (`grep` across `apps/web/src`: only the `index.css` definition). Still physically in
   `index.css`; drop it there when that file is next edited.
7. **Chevron falsifiable criterion** added verbatim: fewer than 4 of 5 participants
   independently read a wait-window row as tappable without prompting → restore an
   explicit affordance (a `+`, not the `›`).
8. **Latin-script scope note** added to `## Type` — an M2.5 decision, not a permanent
   assumption; Indic-script/localised typography revisited before regional-language
   content. Font asset unchanged.
9. **No markdown cleanup needed** — scanned all three docs; no stray SVG, no malformed
   tables (8 balanced code fences).
10. **New `## Authority and conflict resolution`** near the top — table mapping each doc
    to what it owns (from `CLAUDE.md` § "Repo layout"); the two existing conflict rules;
    the new general rule **"if two docs conflict, flag it and ask — never silently pick
    one."** Records that **there is no `DECISIONS.md`** and where decision history
    actually lives.

Plus one consistency fix found during the pass: `## Radius and elevation` said
"`3px --color-signal` for the mainline" while the connector table says 6px with the
rationale that 3px read too weak — aligned to point at the 6px (propagating a decision
already made in the same file, not a new one).
