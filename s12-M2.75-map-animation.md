## 1. The reconciliation

The handoff's animation brief predates Decision 4 (`DESIGN_SYSTEM.md` § *Resolved in
M2.75, round 2*), which removed the time axis entirely. Its literal instruction — scale
an axis in over ~500ms, then fade cards/arrows over 150ms — has no element left to
animate. Replacement, argued as reversal 7 in the same table: **the cards themselves
sweep top-to-bottom**, each fading in over 150ms with a delay proportional to its own
`y` (0ms at the top, 350ms at the bottom, landing at ~500ms — the same duration and
direction the axis sweep had), then dependency edges, window brackets, and fold labels
fade in together once every card has landed. No new visual element; the sweep animates
a fact the static grammar already draws (vertical order carries "when").

Full plan (entry sequence, timing table, per-mark behaviour, reduced-motion, CSS-vs-JS
rationale, file list, test list) is at
`C:\Users\ashya\.claude\plans\continue-gleaming-catmull.md`, approved by the owner.

## 2. Implementation

- **`apps/web/src/map/motion.ts`** (new) — `FADE_MS` (150), `SWEEP_MS` (350),
  `CONNECTOR_DELAY_MS` (500), and the pure `entryDelayMs(y, mapHeight)`. A module-load
  assertion enforces `CONNECTOR_DELAY_MS >= SWEEP_MS + FADE_MS` so a connector can never
  animate in before its endpoints exist.
- **`apps/web/src/map/MapView.tsx`** — `TaskCard` takes `mapHeight` and applies
  `className="map-enter"` with an inline `animationDelay` from `entryDelayMs`. Edges +
  brackets are wrapped in one `<g className="map-enter map-enter-late">`; fold labels
  get a second `<g>` with the same classes, kept *after* the cards in paint order so
  the pre-existing z-order (folds draw on top of cards) is unchanged even though folds
  now share the connectors' fade timing. Legend untouched — no animation classes.
- **`apps/web/src/index.css`** — `@keyframes map-fade-in`, `.map-enter` (150ms
  ease-out, `both` fill mode so cards start invisible during their delay),
  `.map-enter-late` (500ms delay). Also closed a real gap in the existing
  `prefers-reduced-motion` block: it zeroed `animation-duration` /
  `transition-duration` but not `animation-delay`, which combined with `both` fill
  mode would have held reduced-motion users on an invisible card for up to 500ms.
  Added `animation-delay: 0ms !important`.
- **`apps/web/src/map/motion.test.ts`** (new, 18 tests) — `entryDelayMs` boundary/
  monotonicity/clamping behaviour; the `CONNECTOR_DELAY_MS` invariant; a run of
  `layoutMap` over all six golden fixtures asserting every card's delay is in
  `[0, SWEEP_MS]` and non-decreasing when sorted by `y` (so a future layout change that
  breaks the sweep ordering fails here, not just by eyeball); and a same-file check
  that `index.css`'s literal durations/delays match the `motion.ts` constants, so the
  two can't silently drift.

**Not touched, as scoped:** `layout.ts`, `layout.test.ts`, `PlanScreen.tsx`, `App.tsx`,
fixtures, `apps/api`, `packages/schema`.

## An implementation detour worth recording

The plan's original test design read `index.css` via a Vite `?raw` import (avoiding a
Node-types gap in `tsconfig.app.json`, which only declares `types: ["vite/client"]`).
That failed silently at runtime — `?raw` on a `.css` file returns an **empty string**
under this project's Tailwind v4 setup (`@tailwindcss/postcss`/`@import 'tailwindcss'`
in the file), confirmed by isolating the same `?raw` suffix against a `.ts` file (which
returned real content) versus `index.css` (0 characters, silently, no error). Reverted
to `node:fs`/`node:url`, which needed a `/// <reference types="node" />` in the one test
file rather than adding `"node"` to `tsconfig.app.json`'s global `types` array — keeps
the browser-app tsconfig from gaining ambient Node globals for the one file that
legitimately needs them.

## Round 2: real mid-flight visuals, derived connector timing, once-per-recipe

The owner reviewed round 1's evidence and correctly rejected `getAnimations()` timing
data alone as insufficient ("I need to actually see the sweep, not just trust the
timing data"). This round: got genuine mid-animation screenshots via deterministic
frame-stepping, fixed the connector beat's fixed 500ms delay to derive from each map's
real sweep, and implemented once-per-recipe per the round-1 recommendation.

### Getting real visual evidence

CDP screenshot round-trips are too slow/flaky to land inside the ~650ms animation
window at normal speed. Used `element.getAnimations()[0].pause()` +
`.currentTime = <ms>` instead: pausing an animation lets its `currentTime` be set to
any value deterministically, so the frame is frozen *before* the (slow, sometimes
30s-timing-out) screenshot call runs — no race with wall-clock time at all. Captured
Kadai Paneer at t=100/200/300/400/470/650 and Chicken Biryani at t=200/480/700 (top and
bottom of each map), saved to `docs/design/renders/m275-anim-v2-*.jpg`. All show a real
opacity gradient consistent with each card's computed delay — not just the numbers.

**A wrong assumption caught by this exercise:** round 1 characterized Kadai Paneer as
short ("cards complete ~260ms") based on a viewport that was never scrolled past
"Make kadai masala." Kadai Paneer actually has **10 tasks**, not the 6–7 seen before —
`Add veggies`, `Add paneer`, `Finish` continue below the fold, and its real max card
delay is 316ms, nearly as tall a sweep as Biryani's 325ms. Caught by reading the SVG's
own `<desc>` ("10 tasks over 34 min") and the full card list during this round's
verification, not assumed from an old partial screenshot. This changes the practical
answer to "does time-flows-down read on a short map" — none of the six fixtures is
actually short enough for the fixed-500ms dead hold to have been large; Maggi (4 cards,
serial) is the one genuinely short map, and its connector delay dropped from 500ms to
411ms under the new derivation — the most real savings measured.

### 1. Connector/bracket/fold timing — derived, not fixed

`CONNECTOR_DELAY_MS = 500` in `motion.ts` was a fixed constant. New requirement (no
dead hold, no risk of connectors preceding a tall map's last card) makes a *single*
constant impossible to get right for every map, so the fix removes it. **`motion.ts`
change** (explained to the owner before making it, per instruction): removed
`CONNECTOR_DELAY_MS` and its invariant assertion; added
`connectorDelayMs(cards: {y: number}[], mapHeight: number): number`, a pure function
= `max(entryDelayMs(card.y, mapHeight) for card in cards) + FADE_MS` — exactly the
last card's landing time, computed from data already available, no new concept.
`layout.ts` untouched — it has no timing concerns.

`MapView.tsx` computes `connectorDelayMs(layout.cards, layout.height)` once and applies
it as an inline `animationDelay`, same pattern already used per-card. `index.css` lost
the now-nonsensical `.map-enter-late { animation-delay: 500ms }` rule (a fixed CSS
value can't express a per-map computed number); its comment explains why the delay
lives in JS now.

Measured on real fixtures (all satisfy `connectorDelay = maxCardDelay + FADE_MS`
exactly, verified both by `motion.test.ts` and live `getAnimations()`):

| Fixture | Max card delay | New connector delay | Old fixed delay | Dead hold removed |
|---|---|---|---|---|
| Maggi (4 cards, serial) | 261ms | 411ms | 500ms | 89ms |
| Kadai Paneer (10 cards) | 316ms | 466ms | 500ms | 34ms |
| Chicken Biryani (10 shown, 14 total) | 325ms | 475ms | 500ms | 25ms |

`motion.test.ts`: replaced the `CONNECTOR_DELAY_MS` tests with `connectorDelayMs` unit
tests (empty-array case, order-independence, exact-match against `entryDelayMs`) and a
per-fixture test asserting `connectorDelayMs(layout.cards, layout.height)` equals
`max(card delay + FADE_MS)` for all six golden fixtures — the invariant, not just an
example. The CSS-sync test now asserts `.map-enter-late` does *not* reappear in
`index.css` (regression guard against the delay silently moving back to a static rule).

### 2. Once per recipe

Verified the lifecycle claim from round 1 before touching `PlanScreen.tsx`: `App.tsx`
has no `{kind:'plan'} → {kind:'plan'}` transition — every recipe change necessarily
passes through `{kind:'loading'}` (`<Centered>`, a different component at the same JSX
slot) first, which unmounts `PlanScreen` and gives the next recipe a fresh instance.
Toggling `mode` only flips local state in the same instance. So a value that lives in
`PlanScreen` and isn't touched by the `mode` toggle itself is exactly "once per recipe."

**Tried `useState` first — it's actively wrong, not just non-idiomatic.** Flipping
state in a `useEffect` right after the animated mount commits re-renders the same,
still-mounted `MapView` with `skipEntryAnimation=true` almost immediately (well before
the 150–650ms animation finishes), which strips the animation classes off
already-animating elements and snaps every card to full opacity — defeating the
animation on the one mount it's supposed to play on. Confirmed this reasoning applies
before shipping it, not after a bug report.

**Used `useRef` instead** — its mutation triggers no re-render, so flipping it
immediately after mount is inert until `PlanScreen` re-renders for some *other* reason
(the next toggle), which is exactly the needed property. This is a deliberate,
documented exception to oxlint's `react(refs)` "don't read refs during render" rule
(suppressed with `eslint-disable-next-line react-hooks/refs` and an inline comment
explaining why); oxlint stayed at the same four pre-existing, unrelated warnings.

`MapView` gained a `skipEntryAnimation` prop: when true, no `.map-enter` class or
`animationDelay` style is applied to any card or connector group at all — default SVG
opacity is 1, so "skip" needs no CSS, just the absence of the animation classes.
