## Outcome

**Design approved, no implementation.** Owner chose to start M2.9 (YouTube URL → Plan
view import) before M3 (Cooking Mode), on the reasoning that the scheduler is only
proven on hand-authored fixtures until a real recipe enters it. This session ran Step 0
(premise validation against 15 real YouTube URLs), wrote `docs/M2.9-youtube-import-design.md`,
took it through two revisions against owner feedback, ran the two owner-mandated
verifications, and ended with Revision 2 explicitly approved for implementation
planning. No repo code, schema, fixture, or frontend files were touched — the design
doc was the only permitted change, per the owner's explicit scope lock this session.

## 1. Step 0 — premise validation before designing

Per owner instruction, wrote a throwaway (non-repo) `yt-dlp` dump script and ran it
against 15 real YouTube URLs the owner supplied, with no parsing and no LLM — title,
description, channel, duration, and any links found in the description, by hand.

Bucket findings:

| Bucket | Count | Description |
|---|---|---|
| A | 2/15 | Full recipe with durations, no blog link needed |
| B | 2/15 | Rich recipe + chapter timestamps |
| C | 6/15 | **Ingredients-only — no method text, no blog link** |
| D | 2/15 | Method needs a linked blog page |
| E | 3/15 | Useless (no usable signal at all) |

Bucket C — 40%, the single largest bucket — was not anticipated by the owner's original
two-bucket prior (full recipe vs. needs-blog-link). This became the design's central
constraint: the description+blog-JSON-LD acquisition legs have a coverage ceiling of
~40%, and the remaining 60% (mostly bucket C) cannot be handled by inventing a method —
only by refusing to build a graph at all (Tier 0).

## 2. Design doc, revision 1

Wrote `docs/M2.9-youtube-import-design.md` covering architecture-as-found, the proposed
pipeline (acquire → normalize → [review seam] → graph → validate → schedule → Plan),
the extracted/inferred/forbidden field table, the LLM provider cost comparison, and
seven decisions framed for owner ruling. Governing principle, in the owner's words:
*"Optimize what we understand; do not hallucinate what we don't."* Corollary adopted
into the design: uncertainty must cost parallelism, never safety.

Owner rejected one recommendation outright: inferring a small numeric `max_lead_min`
(e.g. 0–2 min) whenever a freshness phrase like "serve immediately" appears but no
number is stated. Explicit instruction: never invent a number; keep `max_lead_min`
null and preserve the textual constraint instead, since a wrong small number is worse
than an honest "unknown but real" gap.

## 3. Design doc, revision 2

Rebuilt around that correction and six other owner rulings:

- **Tier 0 / 1 / 1.5 degradation model** (new this session): Tier 0 = method not
  grounded → refuse the graph entirely, not even a linear one (bucket C's outcome).
  Tier 1 = graph invariants fail even after repair → degrade to a linear chain built
  from the actual stated steps. Tier 1.5 = graph validates but rests on inferred
  scheduling-relevant fields → ships with a warning and `review_recommended=true`,
  under a mandatory per-field conservative-behavior table (§4.7) — window-host duration
  takes the low end of the range, dependencies default to sequential unless
  independence is proven on both ingredients and `produces`, station defaults to
  `burner` for an unknown heat verb, `interruptible=False` when uncertain.
- **Three-valued freshness** (`none` / `stated_unbounded` / `stated_numeric`): the safe
  degradation for a stated-but-unbounded freshness constraint is a *structural*
  `depends_on` edge onto the consumer's other dependencies, not a guessed number —
  mirrors what the existing scheduler's `freshness_ready()` already does dynamically,
  expressed statically. `CookingGraph.max_lead_min` itself stays untouched this
  session; the schema addition is documented, not built.
- Chapter timestamps: grounded but stage-level, used only to corroborate summed node
  durations — never written into `Node.duration_typical`.
- Human review/accept stage: architectural seam only — `normalize.py` must produce a
  real, inspectable `NormalizedRecipe` value before graph construction, but no review
  UI, endpoint, or persistence is built in M2.9.
- `NormalizedRecipe` is a real Pydantic model (not transient) since it's part of the
  `ImportResult` API response the UI will show.
- API shape: `POST /import {url} → 202 {job_id}`, `GET /import/{job_id}` polling — not
  blocking — with an in-process job dict (not the M5 persistence design).
- Provenance lives in a sibling `GraphProvenance` record keyed by `node_id → field →
  extracted|inferred|defaulted`, mirroring the existing `StageSpan` precedent, so
  `Node` and the golden fixtures stay byte-identical.

## 4. The two mandated verifications

**Verification A — blog JSON-LD (run, confirmed):** fetched both Step 0 blog links
directly (`chefkunalkapur.com` via `urllib`; `bit.ly` redirect via `curl -sL` after
`urllib` hit a local `SSLCertVerificationError`) and parsed `<script type=
"application/ld+json">` blocks by hand. Both carry valid, rich `schema.org/Recipe`
JSON-LD — the Rasgulla page via nested `HowToSection`/`HowToStep`, which is *better*
grounding than the raw description text (structured, in-step durations). Recommends
`httpx` + `certifi` for the real implementation to avoid the same cert issue.

**Verification B — multi-script extraction experiment (could not run, reported as
such):** owner explicitly forbade fabricating or simulating this result. Checked this
machine for any usable provider: no `ANTHROPIC_API_KEY` / `OPENAI_*` / `GOOGLE_*` /
`LLM_*` env vars, no `.env` file anywhere in the repo (`apps/api/.env`, `apps/web/.env`,
root), no `ant` CLI or OAuth profile, no provider SDK in the venv, and Ollama installed
with zero models pulled. Reported this plainly rather than guessing at extraction
quality. Consequence: the provider recommendation (Haiku 4.5 extract / Sonnet 5 repair)
stays **provisional** — not a validated product decision — until this experiment
actually runs.

## 5. Approval

Owner approved Revision 2 for implementation planning, with the provider choice
explicitly flagged as provisional, and restated eleven "locked principles" spanning the
governing principle, the Tier 0/1/1.5 definitions, the max_lead_min-never-invented
rule, the freshness three-valued representation, the review-seam-is-architecture-only
boundary, `ImportResult` as a separate envelope, description+JSON-LD as the first (not
final) acquisition strategy, and chapters-as-corroboration-not-duration. Also
reiterated the M2.9 scope fence: no Instagram/TikTok/native share/Cooking
Mode/grocery/meal-planning creep, and no change to `RecipePlanResponse`,
`schema/graph.py`, `schema/node.py`, the scheduler, or the six golden fixtures without
a concrete test proving the change necessary.
